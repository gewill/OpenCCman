## 样本与比较方法

短稿为下列文字，末尾附 **CRLF**，UTF-8 共 47 字节：

```text
滑鼠裡面的軟體，著衣與衞生紙。
```

大文件将完整的 47 字节行重复 245,412 次，共 **11,534,364 字节**，超过工作区 10 MiB 上限，实际进入“大文件直接转换”而非编辑器预览。它用于配置传递和完整输出验证，不是代表性文稿性能测试，也不证明 1 GiB 容量上限。

| 配置 | 短稿预期（末尾仍为 CRLF） | 编辑器复制 | Services API | 大文件保存读回 |
| --- | --- | --- | --- | --- |
| `t2s` | 滑鼠里面的软体，著衣与衞生纸。 | 通过 | 通过 | 通过 |
| `tw2s` | 滑鼠里面的软体，着衣与衞生纸。 | 通过 | 通过 | 通过 |
| `tw2sp` | 鼠标里面的软件，着衣与衞生纸。 | 通过 | 通过 | 通过 |
| `hk2s` | 滑鼠里面的软体，著衣与卫生纸。 | 通过 | 通过 | 通过 |

- 编辑器：通过实际设置控件切换来源／用词，转换，点击“复制结果”，读取 pasteboard 后比较完整字节；四个输出互不相同。来源改变后可见旧结果设置过期提示。
- Services：同一独立 QA 服务进程内用设置控件依次改变四种配置，以仓库 `tests/Benchmarks/ServicesWaitProbe.swift` 调用 `NSPerformService`，各一次。所有调用返回 true，输出全文哈希匹配；另检查 QA 窗口显示当次原文和结果。API 调用往返分别为 177.633、175.070、176.192、172.937 ms；单次样本不作性能统计，亦不代表宿主菜单响应时间。
- 大文件：每种配置均实际点击“导入 TXT”，选择同一 11 MiB 输入，核对任务摘要，选择不同输出文件，点击“转换并保存”，观察“转换完成”后读取完整文件。没有覆盖原文件，也没有把全文装入编辑器。`tw2sp` 首次比较失败后又在完成状态读回，仍有同一差异，随后定位为下面的预期文件问题；不以文件存在代替完成状态。
- 香港来源下保留的“台湾用词”选项变灰；Services 与大文件实际输出均是 `hk2s`，没有误用保留值。

## 命令行预期文件与整篇 API 的差异

最初以本机 OpenCC 1.4.2 的 `opencc -i` 生成完整文件预期。`tw2sp` 大文件比较发现 **6 字节不同**，始于零基字节 8,388,560：App 将该行的“滑鼠”转成“鼠标”，CLI 文件模式在那里保留“滑鼠”。其余位置及文件长度相同。

重复运行相同 CLI 命令得到同一差异。[官方 1.4.2 文件模式源码](https://github.com/BYVoid/OpenCC/blob/ver.1.4.2/src/tools/CommandLineMain.cpp#L544) 使用 1 MiB 读取和 `ConverterStream`；本轮没有将其内部词组边界处理隔离复现，**具体根因未定位**，不能断言它完全不保留词组上下文。实测已足以证明本机 CLI 文件模式输出不能直接作为这个样本的整篇预期。

复核使用同一 OpenCC 1.4.2 动态库，对完整 11,534,364 字节输入执行 **一次 `opencc_convert_utf8`**，同时用完整短行结果重复拼接作独立对照。两者四个配置全部一致；App 的四份保存文件也全部一致。`tw2sp` 正确整篇结果 SHA-256 为 `3f3987e4ab3b3ba809930256a9c216f88d868973db9817d9e8f1680f966c90c8`，原 CLI 文件模式结果为 `4cdcbfb12d13b00626a63ecd4a794faa6741e43bce33b1300e07ff9587756ed7`。两份原件和首次失败记录均保留，没有回写原始失败为通过。

本机整篇参考库为 OpenCC 1.4.2，动态库 SHA-256 `28239d88b24af76c58ecd29bb9c8c49b4d07866c48600fdf9bd8af3db5ce40fd`。这是独立上游库输出比较，不冒充与 App fork 同一二进制。本轮不修改 OpenCC 上游 CLI。

## 隔离环境排障

**Services 注册：** 主 QA 的五次调用均返回 false、pasteboard 原文未变。刷新注册、恢复原端口和撤销本任务未启动构建副本的注册均未解决；没有清空全局数据库或注销其他任务的包。Launch Services 中存在多份历史包共用 `WhatsNewUITests` Bundle ID。换成独立 Bundle ID 与唯一服务名／端口后，四次调用通过。这支持隔离注册冲突的判断，但并未逐一注销历史包证明唯一因果。不能据此宣称已修复正式 App 的 Services 缺陷。

**辅助功能授权：** 用户只授权本次隔离验收，并亲自完成系统身份验证。系统开关开启后 App 仍报告未授权，刷新和重启无效；TCC 日志明确记录旧 `cdhash 62d9…` 与当前签名不匹配。经系统设置移除该 QA 项、重新选择同一准确 App 路径后，App 显示“辅助功能权限已授予”。未修改 TCC 数据库、放宽签名要求或为 Services 对照包授权。

**全局按键：** CUA 向 TextEdit 测试稿发送 ⌥⌘T 后没有触发转换；选择文字仍完整，QA 未收到结果。正在等待手动按键对照，尚不能区分工具事件投递、焦点／快捷键占用与 App 行为。权限开启不等于全局快捷键通过。四个配置均列为未验证，不用 Services 或编辑器结果替代。
