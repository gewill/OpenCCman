# Mac 应用内文字大小验收（#191 / #57）

## 实现范围

macOS 设置页提供全应用共用的 100%／125%／150% 文字大小，默认 100%。这一偏好只影响 OpenCCman 自身，不改变系统显示设置、图标尺寸、每日额度或窗口最小宽度。SwiftUI 文本按语义字级缩放；原文与结果仍是同一原生 `NSTextView`，字号更新时保留文本、选区和可见首行，并在输入法标记文字期间延后重排。iOS/iPadOS 继续使用系统 Dynamic Type。

提供应用内入口的原因是 [Apple 对 macOS `dynamicTypeSize` 的说明](https://developer.apple.com/documentation/swiftui/environmentvalues/dynamictypesize)：用户不能在 macOS 上修改它，改变它也不会影响文字大小。此前 #57 在 macOS 27 把系统文字滑杆调到最大后，同一应用窗口截图仍逐字节相同；本次没有把该系统设置当成验收路径。

## 运行证据

| 项目 | 结果 |
| --- | --- |
| 修改前 | `develop` `0e6ff558720a0f552718bd9199604f358c05323e`；Mac 设置页无文字大小入口 |
| 修改后截图来源 | 候选应用源码 `218e2d8c1cd02373d0d59221cf132714cd8d5a4c`；后续提交仅增加本报告 |
| 环境 | macOS 27.0、Xcode 27.0（27A266a）、英语、浅色；两份独立 ad-hoc 签名 Debug QA 应用，均为 1024×768 pt 窗口 |
| 隔离 | 基线与候选使用不同 QA bundle ID；复制件移除 `NSServices`，保留沙盒 entitlement；签名深度校验通过。未运行或修改正式签名 App |
| 工作区 | 同一内置中文样例在修改前 100% 与修改后 150% 各执行一次转换，结果一致；候选文字、按钮与说明自然增高，原文和结果 AX 值保持可读，复制／导出入口启用 |
| 设置 | 100%→150% 切换后 AX 单选状态正确；返回工作区时原文、结果仍在，未触发第二次转换 |
| 额外界面观察 | 候选在 1024×768 pt 下切换过左右／上下布局、打开转换设置，并在深色外观查看 150% 的双栏原文和结果；文字与结果颜色可读。这些观察没有覆盖下述完整矩阵 |
| 回归 | Mac/iOS Simulator Debug 完整构建、项目与本地化检查、工作区和窗口尺寸检查、控件尺寸检查通过；编辑器检查覆盖 1/10 MiB 输入与只读结果的字号切换、选区、撤销、可见首行及输入法标记文字延后更新 |
| 10 MiB 位置恢复 | 同机、同一无窗口 TextKit 回归夹具中，原实现的中段字号切换耗时 24.9–47.7 秒；对纯文本合并字体属性段后，输入／只读结果的四次切换为 0.40–0.44 秒。该数值只描述该夹具，不推断完整 App 的响应时间 |

真实前后截图和设置切换视频经 `gh` 上传至实现 PR；截图各为 2140×1628 像素（含系统窗口阴影），窗口内容实际为 1024×768 pt。视频是同一候选 QA 应用的 1024×768 pt 窗口，持续约 35 秒、无音频和鼠标指针，展示 100%→125%→150% 及返回后已有原文／结果保留。截图使用各自源码构建，没有把先前误用候选源码的基线副本当作修改前证据。

## 尚未验收

- 150% 下 300×412 pt 最小窗口的完整简繁英、浅深色、左右／上下、侧栏、导入导出、Pro 与 VoiceOver／键盘矩阵尚无本次运行证据。1024 pt 下的部分左右／上下、设置与深色观察不能替代该矩阵。窗口缩放的自动化拖边未命中系统边缘，因此不能从 1024 pt 截图推断最小窗口通过。#191 保持开放，验收完成后再回链 #57。
- 本机当前只有内建逻辑显示器，物理外接显示器断开／重新接入仍按 [#57 运行手册](../window-sizing/physical-display-reconnect.md) 保留。macOS 12 最低系统与正式签名包仍是发布前验收项。
