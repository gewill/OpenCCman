# OpenCCman 项目完成度、验证证据与后续修改建议

核对日期：2026-09-13（Asia/Taipei）。本文是截至下列提交的状态快照，汇总项目审查、1.3 功能、引擎迁移和两仓库同步交付。后续 PR 不自动改变本文中的验收结论。

## 1. 结论与适用范围

**源码审查、已确认问题修复、1.3 功能、OpenCC 1.4.2 迁移及同步流程主体已交付并合并；发布前验收及部分原计划中的可重复验证要求尚未全部完成。** 不能把 CI 成功等同于购买、分发签名、跨 App 行为和旧系统真机均已验收。

本次核对还发现两个需要明确补记的计划差距：资源生成使用环境中的 CMake，尚未锁定其版本并保存完整生成工具信息；官方模式已对照同版本官方测试语料，但尚无直接调用同版本官方 CLI 做差分比较的交付证据。它们分别列入 R4、R5，不再笼统归为“全部完成”。

原始全量审查覆盖当时全部 43 个 Swift 文件、3956 行代码和 88 个受跟踪文件。该数字属于审查基线，不是新增功能后的文件总数。第三方依赖审查覆盖实际使用接口、锁定版本、许可证及已定位问题，未审计所有依赖的每一行源码。本报告是既有工作与当前实现的证据核对，本次仅修改文档。

## 3. 已有验证证据及其边界

### 应用

[App Regression：报告基线 build 提交](https://github.com/gewill/OpenCCman/actions/runs/34687985512) 已成功。该 job 覆盖工程/源码检查、真实转换与模型/文件流程、额度预约以及隔离剪贴板回归。

已有行为覆盖包括：七组配置 × 八类语料；空输入和长文本边界；取消/替换/释放模型；导出快照；UTF-8/BOM/CRLF/组合字符/NUL；大小上限及非法编码；NSURL/NSString 拖放 provider；provider 不回调时的取消；两个窗口争用最后额度；100 次并发预约；跨日完成及 Pro 路径。

完整 generic macOS 与 iOS Debug 构建曾通过；独立验证 bundle identifier 的 Apple Development 签名版本完成过真实系统文件面板的导入、台湾预设转换、导出、精确字节比较及非法 UTF-8 保留原稿测试。关闭/重新打开窗口的基本行为也有记录。

**这些完整构建及签名文件测试发生在功能交付阶段，不能直接当作最终 1.4.2 依赖分发包的验收记录。** 最终依赖更新通过了锁定解析、真实生产模型/服务编译及核心回归，但仍需 R3 的最终产物验证。基本窗口重开通过也不代表“所有窗口关闭后由 Services／快捷键自动创建窗口”已经实现。

### 引擎

应用当前 pin 的合并后 [OpenCC Compatibility](https://github.com/gewill/SwiftyOpenCC/actions/runs/34683641237) 成功；最新仅文档变更的 master [检查](https://github.com/gewill/SwiftyOpenCC/actions/runs/34687981182) 也成功。

已有证据包括资源 `--check`、Git revision 消费者解析、7 个 SwiftPM 测试中的组合/语料/生命周期/并发场景、ASan、TSan，以及 iOS 14 目标的引擎编译和完整对象链接。引擎 API/词库输出变化、未公开支持的 `tw2t` 等模式与 NUL workaround 均有 [迁移记录](https://github.com/gewill/SwiftyOpenCC/blob/eacb73dcb28c26e7cc5d8d9cb405e88fa2d59b13/docs/opencc-1.4.2-migration.md)。

Git revision 清单曾因虚拟文件系统中的 `/Package.swift` 无法读取相邻资源而失败，已经修复并加入回归。现有包清单使用纯声明版本常量，由生成器校验，不在求值时读取资源 JSON。

### 同步自动化

[首次成功的真实准备与发布](https://github.com/gewill/OpenCCman/actions/runs/34683913795) 由 GitHub App 创建 [应用依赖 PR #5](https://github.com/gewill/OpenCCman/pull/5)，其余 14 个依赖未漂移，PR 与合并后 CI 成功。当次合并后 fork/app 只读检查均为 `noop`。

协调器 fixture 回归覆盖重复运行、待审 PR、人工拒绝、POST 返回不确定、冲突、生成失败、移动 tag、降级/主版本、base 变化、bundle 篡改、外部同名分支、依赖漂移、认证错误及验证进程移除显式 token。真实工作流修复过共享 runner 匿名 API 限额；现在读操作使用认证，验证 job 不持有 App 写令牌。

协调器位于默认 main，每周一 09:17（UTC+8）检查，也可手动运行。检测/验证与短期写令牌发布分离，Actions 固定完整 SHA。它只创建 PR；fork 先以 merge commit 合并且精确 SHA 上 CI 成功，才推进应用依赖 PR。详细规则见 [共用同步指南](https://github.com/gewill/OpenCCman/blob/main/docs/upstream-sync.md)。

**实机工作流证据直接覆盖应用层发布，不能替代未来正式核心升级的自动 fork 层实跑，也没有执行真实仓库回滚演练。** 正常的生产回滚不应为了补测试而无故执行，按 R6 隔离演练。

## 4. 性能结论

| 实测对象 | 旧值 | 新值 | 可支持的结论 |
| --- | ---: | ---: | --- |
| 应用文本处理路径，48 万字符、1,360,000 UTF-8 字节 | 460.77 ms | 154.04 ms | 本机 Release、预热转换器、5 次中位数；旧分块与新全文处理对照，约减少 67% 耗时 |
| 同一应用样本的结果发布 | 121 次 | 1 次 | 减少中间完整结果发布；不是 FPS 测量 |
| 额度查询微基准，2,000 次 | 37.08 ms | 1.95 ms | 日期/计数路径局部改善；不是整应用速度 |
| 引擎冷创建 | 15.31 ms | 30.86 ms | 1.4.2 更慢，需要保留并评估复用策略 |
| 引擎热转换，1,176,000 UTF-8 字节 | 187.58 ms | 15.47 ms | 同机固定语料下约快 91.8% |
| 引擎测试进程峰值 RSS（转换后） | 38.42 MB | 64.93 MB | 内存上升；包含输入/输出缓冲，不等于实际应用 RSS |

应用处理路径和引擎升级是两组不同实验，不能将改善比例相乘，也不能用热转换提速掩盖冷创建与内存代价。原始方法和样本见 [项目审计](project-audit-2026-09-12.md) 与 [引擎测量文件](https://github.com/gewill/SwiftyOpenCC/blob/eacb73dcb28c26e7cc5d8d9cb405e88fa2d59b13/docs/engine-benchmark-1.4.2.json)。尚无最终应用端到端启动、FPS、电量或低端设备收益结论。

## 5. 未完成项与建议修改

优先级用于执行顺序：**P0 发布前必须闭环；P1 补齐原计划的重复验证或行为边界；P2 后续按复现/收益决定。** 下列都是建议或待验收事项，不表示本次已修改代码、已建立任务或已执行购买/发布。

### R1 · P0 · 购买、恢复与资格验收

- **缺口**：代码和测试替身不能证明实际 Offering、商品、交易与资格更新正常；没有真实 Sandbox/TestFlight 流程证据。
- **建议**：使用测试账号验证每张套餐卡片对应的商品 ID、价格展示和购买结果；覆盖取消、失败、断网、恢复、应用重启、退款/资格撤销及已有 Pro 的离线行为。产品类型支持订阅时再测续订/到期，不假设所有商品都是订阅。
- **建议修改位置**：若复现问题，按实际错误定位 `IAPManager`、`ProScene` 或后台 Offering/entitlement 配置；不要无证据更换支付 SDK、价格或交易验证方式。
- **通过标准**：所选商品与实际交易一致；取消不展示失败；失败查询不误降级；有效资格变化能刷新 UI 与额度；恢复由用户主动触发。记录 app SHA、build、系统、商品 ID、操作、预期/实际及脱敏日志，禁止保存账号凭据或完整收据。
- **环境**：优先 Sandbox/TestFlight，无需正式付费交易。Apple 区分本地 StoreKit、sandbox 与 TestFlight 的覆盖范围，不能互相替代。[官方测试说明](https://developer.apple.com/documentation/storekit/testing-at-all-stages-of-development-with-xcode-and-the-sandbox)

### R2 · P0 · 签名分发包的文件与跨 App 行为

- **缺口**：文件面板已测开发签名；Services 和全局快捷键的分发签名/TCC 端到端验证仍缺。事件投递没有粘贴完成回调，当前保留 800 ms 等待，PID/changeCount 不能识别同 App 内所有选区变化。
- **建议**：在最终签名包上验证授权、拒绝、撤销、重新授权；用 TextEdit 和浏览器可编辑区域覆盖选中文字、空选区、连续触发、切换 App、途中再次复制、多格式剪贴板和慢目标 App。再测外部目录 TXT 导入/导出、保存取消、同名文件处理。
- **建议修改位置**：若出现误替换或剪贴板覆盖，在 `GlobalShortcutService` 中收紧操作状态与目标复核；无法可靠判定时建议退回“保留转换结果，让用户手动复制/粘贴”的明确路径。不要仅把等待时间调长后宣称解决竞态。
- **通过标准**：不向已切换的目标粘贴，不覆盖用户后续复制；无法完成时可理解且不丢稿；权限状态与 UI 一致；系统面板读写正确。文件访问应保持用户选定读写范围。[Apple entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.files.user-selected.read-write)

### R3 · P0 · 最终产物、部署下限与发布资料

- **缺口**：早期 Debug 构建、引擎 iOS 14 链接和最终依赖核心回归分别成立，但没有同一最终分发产物的完整验收记录。旧系统实际运行、TestFlight/分发签名和后台发布资料也未闭环。
- **建议**：功能和依赖冻结后，对最终 SHA 做一次必要的完整 Release/Archive 验证，记录 Xcode/SDK、配置、架构、实际 revision 与签名 entitlements。iOS/macOS 按实际发布目标分别生成必要产物，不建立无需求的模拟器矩阵。
- **验收范围**：首启、四预设/高级选项、TXT 流程、大文本取消、12 次额度/Pro、多窗口、购买、Services/快捷键；旧系统设备可用时至少覆盖声明的 iOS 14/macOS 11 路径。设备不可用须明确记录，不能把编译成功写成运行成功。
- **发布资料**：核对 PrivacyInfo.xcprivacy 与 App Store Connect 隐私问卷、商品说明、版本说明和实际权限一致；当前没有证据证明这些后台项已完成。只针对实际差异修改，不自动调价或提高部署目标。
- **通过标准**：同一最终产物通过 R1/R2 及上述关键路径，所有失败有修复或明确的发布决定；保留脱敏验证日志与产物身份。

### R4 · P1 · 锁定资源生成工具并记录完整来源

- **事实依据**：`scripts/update-opencc-resources.py` 直接调用环境中的 `cmake`；现有 manifest 记录核心 tag/SHA、资源哈希、格式和字节序，但没有 CMake 精确版本与完整生成参数记录。固定 macos-15 runner 标签不等于锁定其预装工具版本。
- **建议修改**：在 SwiftyOpenCC 的人工维护 PR 中确定经过验证的 CMake 版本和可校验安装来源；生成器预检版本，将 CMake/编译器/平台信息、实际配置参数和核心 SHA 记录到单独 provenance 文件或兼容升级后的 manifest。将对应检查接入协调器候选验证；同步更新允许变更范围和文档，不能只改 README 声称锁定。
- **通过标准**：错误版本能给出明确错误；清理生成目录后，在同一受控工具环境重复生成两次，资源清单/哈希一致；四份兼容配置未被覆盖；来源记录与实际命令一致；正常只读 `--check` 不被迫启动编译。

### R5 · P1 · 增加同版本官方 CLI 差分验证

- **事实依据**：当前测试读取官方 `testcases.json` 并断言预期输出，覆盖 10 个模式/495 个输出；未找到直接执行官方 CLI 比较结果的检查。
- **建议修改**：在 SwiftyOpenCC 增加独立检查脚本，用已锁定核心构建官方 CLI，对 10 个可表达官方模式运行相同的固定 UTF-8 语料，按字节比较 wrapper 与 CLI 输出。4 个兼容模式继续使用独立固定预期，不伪称存在一一对应官方配置；不要为测试引入新公开选项。
- **NUL 边界**：已知 1.4.2 原生路径的 NUL 截断由 wrapper 分段修复。NUL-free 语料严格对照 CLI；含 NUL 场景单独断言完整输出，并解释与原生差异，不能为追求相等恢复截断。
- **通过标准**：报告核心 SHA、配置、CLI 构建信息、输入/输出哈希及失败差异；错误映射确实能使检查失败；保留官方语料回归，不能静默修改预期掩盖词库变化。

### R6 · P1 · 真实 fork 候选与回滚的隔离演练

- **缺口**：App 发布链已真实跑通；幂等、冲突与回滚忽略规则有 fixture 覆盖，但尚无未来正式核心版本自动生成 fork PR 的真实演练记录，也未在生产执行回滚。
- **建议**：在一次实际可用的后续正式更新上，先运行 `check`/`prepare --stage fork` 检查真实生成与兼容结果；没有新版本时，在隔离的本地/专用测试仓库复用可验证来源演练，禁止移动正式 tag、伪造生产更新或为了演练回退线上依赖。
- **回滚建议**：演练恢复应用旧 revision、必要时撤销整个 fork 同步 merge，并配置对应 `ignoredCandidates`；验证重复检查不会再次提出同一候选，新的来源仍可继续同步。
- **通过标准**：留下来源 SHA、补丁、资源/回归报告、幂等 JSON、回滚后状态及失败恢复记录。机器人继续只开 PR，保持人工合并与读写凭证分离。

### R7 · P1 · 最终应用性能与内存基线

- **缺口**：已有引擎和处理路径样本，未覆盖最终应用启动与多窗口/多配置驻留内存；引擎升级已有冷创建更慢、RSS 更高的事实。
- **建议**：同一机器、相同 Release 配置、固定依赖分别测首次启动、首次转换、热转换、七组配置依次使用、多窗口和大文本处理峰值；保留原始样本、输入哈希、环境及输出正确性。冷启动必须用新进程，不把缓存命中当作冷启动。
- **修改方向**：先确认主线程阻塞或内存峰值来源，再评估转换器缓存的容量/生命周期和文本视图更新。不要无测量删除缓存、恢复破坏词组的硬分块，或把上游宣传数字直接写进应用收益。
- **通过标准**：形成可重复的应用基线及回归判断方法；任何优化给出正确性保持和实测前后结果。未测 FPS/电量时明确留空。

### R8 · P1 · 全部窗口关闭后的系统入口

- **事实依据**：`AppDelegate.activateMainWindow()` 只选择既有窗口；无可用窗口时保存最新通知，窗口就绪后再投递。当前没有显式创建窗口的兼容路径。
- **建议**：先用签名应用复现“关闭全部窗口但进程仍在 → Services/快捷键/状态栏触发”。若请求无法得到可见结果，增加统一且适配 macOS 11 的窗口恢复/创建入口，确保只有一个请求投递目标和一次消费；使用公开、经过验证的窗口生命周期 API。
- **通过标准**：冷启动、全部关窗、Dock 重开、系统入口触发和多窗口分别验收；无重复窗口、无后台不可见扣次、无旧请求覆盖新稿。正常重开已有窗口通过不替代这一组测试。

### R9 · P1 · 可访问性与编辑器运行时检查

- **缺口**：按钮语义和选中状态已修复；没有完整 VoiceOver、键盘焦点及所有支持系统上的 TextEditor Introspect 运行验证。
- **建议**：用最终产物覆盖键盘 Tab/快捷键、焦点顺序、VoiceOver 标签/选中/禁用状态、长文本滚动选取、结果只读、错误弹窗及取消入口。发现缺陷再定向修改 HomeScene、选择控件或编辑器桥接。
- **通过标准**：核心转换/文件流程可通过键盘与辅助技术完成；结果可选取复制且不可编辑；不因可访问性修改影响原输入或格式。

### R10 · P2 · 保留的系统/引擎边界

- **NSServices 同步协议**：当前需返回前写回结果，大文本可能占用服务线程。建议先测目标 App 的等待和超时；若达到不可接受程度，明确容量边界或引导到应用文件流程。不要用阻塞等待异步任务伪装为可取消后台服务。
- **C++ 取消能力**：当前只停止任务后续处理和结果写回。建议保留准确的 UI 语义；只有上游提供可验证的中断接口后再考虑真正中断，不能通过销毁仍在使用的 native handle 实现。
- **未使用依赖/编译警告**：SwiftUIOverlayContainer 无直接使用、颜色符号冲突和部分 Swift 6 预警可单独评估。只有确认收益或实际兼容失败时才清理，不为文档收尾顺手升级依赖或迁移语言模式。

## 7. 建议执行顺序与完成定义

1. **文档收尾**：合入本报告及旧记录更新说明；此步骤不改应用或自动化行为。
2. **可重复升级**：分别以小范围 PR 完成 R4 工具来源锁定、R5 官方 CLI 对照，并安排 R6 隔离演练。它们是原同步计划的未完成要求，不能仅靠应用现有 CI 宣称关闭。
3. **最终产物冻结**：确定要发布的应用 SHA 和引擎 revision；按 R7 建立性能基线，处理实际复现的 R8/R9 问题，再做 R3 必要完整构建。
4. **发布验收**：用该产物完成 R1/R2 和旧系统关键路径；需要修复时建立定向 PR，并只重测受影响流程及最终必要检查。
5. **发布决定**：P0 全部有通过证据；P1 中原计划硬性要求完成，其余行为缺口有验收结果或明确的延期理由；记录剩余限制，才可把“项目全部验收完成”作为结论。

```text

系统、设备/架构、Xcode/SDK、签名类型：
前置条件与操作：
预期结果 / 实际结果：
证据：脱敏日志、截图或 PR/CI 地址
问题及后续修改：
延期理由与影响（如适用）：
```
