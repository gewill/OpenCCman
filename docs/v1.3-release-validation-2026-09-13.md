## 引擎与协调器证据

[SwiftyOpenCC #4](https://github.com/gewill/SwiftyOpenCC/pull/4) 实现 R4/R5，测试记录和精简 CLI JSON 随 PR 提交。CMake 下载和缓存哈希错误会在执行前停止；只读 `--check` 不编译。7 个 Python 测试、7 个 Swift 测试、精确 Git revision 消费者验证通过。CI 保留完整 CLI JSON，失败运行会替换旧的通过报告。

CLI 显式使用 `--include-tofu-risk-dictionaries`，匹配库的现有默认加载选项。初次对照发现 `殢` 的 t2s 差异，根因是 CLI 与库的默认选项不同；未修改词库或预期来掩盖差异。含 NUL 的 wrapper 修复单独断言，不要求与原生截断行为相等。

[协调器 PR #9](https://github.com/gewill/OpenCCman/pull/9) 新增报告存在性、通过状态及核心 tag/SHA 检查，并保留失败 JSON；新增 CLI 命令同样不携带显式 GitHub token。先合入引擎验证工具 PR，再合入协调器 PR。同步仍只提 PR，由维护者合并；没有为演练回滚生产仓库、移动正式 tag 或改写历史。

## Xcode Cloud 失败与修改建议

实际 workflow 为 `00F5435C-1C48-4750-88FA-4563D018E4B3`（Default），App ID 为 `6474449401`，分支前缀为 `build`。run #42 的 SHA 与本地 Archive 源码相同；macOS Archive 成功，iOS Archive 在独立签名 `SwiftyOpenCC_OpenCC.bundle` 时失败，两个 TestFlight 后续动作被跳过。

云端命令使用 `CODE_SIGN_IDENTITY=- AD_HOC_CODE_SIGNING_ALLOWED=YES`。同样设置在本地 SwiftPM/Xcode 构建中复现 `bundle format unrecognized, invalid, or unsuitable`。包声明 `.copy("Resources")` 在 iOS bundle 顶层生成了 `Resources` 目录；仅在隔离副本改名后，原 `codesign` 命令即成功。

[引擎 PR #5](https://github.com/gewill/SwiftyOpenCC/pull/5) 已实现分别复制 `Official`、`Compatibility`、`manifest.json` 并同步 Bundle.module 读取路径，避免这个顶层目录；不改词典内容、不禁用签名、不依赖额外云端证书。新增 iOS 资源 bundle 构建与签名回归已在本地通过，并验证全部 42 个打包文件哈希、manifest 字节和七个 Swift 测试。修复证据随引擎 PR 保存。

这一检查补上了此前开发签名完整 Archive 和父应用验签的盲区。修复后仍需先合并引擎，再更新应用 revision，让 `build` 的下一次 Xcode Cloud run 验证真实分发流程。不能在该 run 成功前宣称云端阻塞已解除。
