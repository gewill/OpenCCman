# #68: 双原生编辑器的清空后内存回落

两个并排、各 440pt 宽的原生 `NSTextView` 同时处理同一份 1 MiB 文稿，清空 30 秒后的 TextKit 2 物理内存占用在三个新进程中为 **267.9–269.4 MiB**，中位数 268.6 MiB；TextKit 1 为 **73.8–75.1 MiB**，中位数 74.6 MiB。两种模式均没有出现[应用双编辑器实验](../2026-09-24-recovery-retention/README.md)中 TextKit 2 的约 189 / 382 MiB 高低分叉。**两个原生编辑器本身没有在此协议中重现该分叉**；应用仍有不同文本、转换、布局切轴和 SwiftUI 桥接，不能由这些进程总量推算其中任何一项的成本，也不能断定某一项就是原因。

## 实验边界

私有原生驱动提交 `125862843a9d7ab7d30facf1e4ec229310377166`。与[单原生编辑器对照](../2026-09-24-native-recovery-control/README.md)同机、同工具链、同输入 SHA-256 `3589430ad438ead1803658c8c0d77d32d30f5694b0b1787ffc512d4e32f8b239`，每组按 TextKit 1 → TextKit 2 交错启动新前台进程。窗口内容为 880×800pt，两个编辑器的可用视口均为 440pt。两者各自设置相同原文、确认开头／中部／文末目标进入各自视口，再同时清空并等待 5 秒和 30 秒。此控制特意使用相同文本；应用右侧编辑器装载的是转换结果，故不声称逐字节同构。

| 清空后的物理内存占用，MiB | TextKit 1（n=3） | TextKit 2（n=3） |
| --- | ---: | ---: |
| 清空前中位数（范围） | 238.9（238.1–242.4） | 447.3（441.8–447.9） |
| 清空 5 秒中位数（范围） | 78.9（78.1–79.4） | 272.8（272.1–273.6） |
| 清空 30 秒中位数（范围） | 74.6（73.8–75.1） | 268.6（267.9–269.4） |

六个进程均完成协议、窗口可见且全程前台；TextKit 2 的两个编辑器都有 `textLayoutManager`，无兼容模式回退通知。每次清空后，两个编辑器的 `string` 与 `textStorage` 都为零长度。此处较高的物理内存占用不是泄漏证明；本轮没有采集双原生编辑器的 heap 引用树。原生单编辑器的 30 秒中位数分别为 52.1 / 169.3 MiB，应用双编辑器为 212.2 / 381.7 MiB（其中 TextKit 2 高低状态并存）。这三种进程的窗口树、文本和操作协议不相同，**不相减解释“桥接开销”**。应用高状态已有两条来自活跃编辑器的布局片段引用链；还需逐编辑器对象计数和相同内容／操作路径，才能解释状态分化。

## 复核

[`raw/`](raw/) 保存六份逐阶段运行数据、三份构建元数据、三份驱动汇总、压缩输入和 SHA-256 清单。校验脚本锁定源码提交及环境、检验同一原文和视口、双编辑器前台／模式／选区可见性／清空状态，并重新验证单编辑器与应用归档：

```bash
python3 docs/performance/2026-09-24-native-paired-recovery/analyze.py
python3 scripts/measure-native-textkit.py --output /path/outside/repo --pattern app-mixed --sizes 1 --samples 3 --modes tk1 tk2 --recovery --second-editor --activate-process --content-width 440 --timeout 120
```

数据来自三个单样本输出目录；复跑命令使用相同交错顺序，但新进程数据不会数值完全相同。驱动只要求 System Events 激活它刚启动的诊断 PID；前台失败即排除。仍需采集原生双编辑器 heap／VM 及应用逐编辑器引用计数，使用真实转换结果和同等布局动作复测，再覆盖普通 TXT、5/10 MiB、编辑／IME、iOS 15／macOS 12、VoiceOver 与签名包。#68 保持开放，正式应用继续使用 TextKit 1。
