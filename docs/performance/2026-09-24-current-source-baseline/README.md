- 从仓库外的隔离目录执行 `python3 scripts/benchmark-app.py --output /tmp/openccman-18-current-20260924 --packages /tmp/openccman-22-sourcepackages --build-only`，再用 `--reuse-build --samples 5 --timeout 180` 运行。重新生成时可换成自己的仓库外目录和已解析依赖目录。驱动会拒绝源码、依赖或产物哈希变化，并拒绝覆盖已有样本。
- [`run-01.json`](run-01.json) 至 [`run-05.json`](run-05.json) 均为 `complete`，各有相同顺序的 36 个阶段，均对应同一个 metadata SHA-256。首次及 1/5/10 MiB 转换的编辑器文本与模型、导出内容与结果均一致；五轮输出哈希分别相同。两轮关闭托管额外窗口后，额外模型存活数均为零。这些是诊断协议的检查，不等于原生 `WindowGroup` 或签名发布包的验收。

## 判断边界与后续

“进程至根布局”包含 LaunchServices 的 reopen 握手，未清空系统／文件缓存，因此不能称作真实冷盘启动或首帧呈现时间。转换时间止于业务模型完成；布局 flush 的诊断标记也不等于用户看见最终画面。诊断包使用 ad-hoc 签名、关闭 sandbox、合成 Pro 状态，并抑制部分网络／弹窗行为；RSS 高水位包含前序阶段和测试语料，不可把 10 MiB 阶段全部内存归因给编辑器或 OpenCC。

此前 [PR #124](https://github.com/gewill/OpenCCman/pull/124) 已为原生 `WindowGroup` 模型释放提供定向回归证据，因此 #18 旧文案“原生窗口释放未验证”需要按该证据修正；本轮托管窗口数据不能替代它。最终签名 2.0 包、最低 macOS 12／iOS 15、真实设备和购买／登录场景仍另行验收。后续性能改动应在相同源码基线、协议、机器和条件下做 A/B，对正确性、时间分布与 RSS/footprint 同时复测；没有成对样本时保持 #18 开放。
